Coordinate Systems and Transforms

Every game uses multiple coordinate systems. Understanding the relationships between them is essential for input handling, rendering, camera systems, and spatial logic.

The Five Coordinate Systems

Input vs Screen Coordinates

Input coordinates come from the operating system and are relative to the window's client area. Screen coordinates are relative to the rendering viewport.

In most cases, these are identical. They differ when:

  • The game renders to a smaller viewport than the window (letterboxing/pillarboxing)
  • Multiple viewports are used (split-screen games)
  • UI overlays consume part of the window
  • Platform-specific window decorations affect coordinate systems
// Convert input to screen coordinates when they differ
var inputPos = new Vector2(Mouse.GetState().X, Mouse.GetState().Y);
var screenPos = inputPos - viewportOffset;  // Adjust for viewport if needed

Y-Axis Orientation

In computer graphics, the Y-axis typically points downward from the top-left origin. This is why:

  • Mouse.Y = 0 is at the top of the window
  • Increasing Y values move down the screen
  • Grid row 0 is typically at the top

For grid-based games with integer positions, ensure your units respect grid alignment:

// For units constrained to grid cells
var unitGridPosition = new Point((int)worldPosition.X / cellSize, (int)worldPosition.Y / cellSize);

// Position unit at center of grid cell
var unitWorldPosition = new Vector2(
    gridPosition.X * cellSize + cellSize / 2f,
    gridPosition.Y * cellSize + cellSize / 2f
);

Transform Matrices

MonoGame's SpriteBatch accepts an optional transformMatrix parameter that applies a linear transformation to all drawing operations within the Begin/End block.

spriteBatch.Begin(transformMatrix: transformMatrix);

Transform matrices can combine translation, rotation, and scaling in a single operation. For 2D games, we typically use 3×3 matrices (with implicit homogeneous coordinates).

Translation Matrix

| 1  0  tx |   | x |   | x + tx |
| 0  1  ty | × | y | = | y + ty |
| 0  0  1  |   | 1 |   |    1   |

Move coordinates by tx horizontally and ty vertically.

Scaling Matrix

| sx 0  0 |   | x |   | x × sx |
| 0  sy 0 | × | y | = | y × sy |
| 0  0  1 |   | 1 |   |    1   |

Scale coordinates by sx horizontally and sy vertically. Used for zooming camera.

Combining Transforms

Multiple transforms can be combined by matrix multiplication. Order matters because matrix multiplication is not commutative.

For camera transforms, use: Scale first, then Translate

// Pan camera by (100, 50) and zoom to 2x
var scaling = Matrix.CreateScale(2f);
var translation = Matrix.CreateTranslation(-100, -50, 0);
var transform = scaling * translation;  // Scale first!
spriteBatch.Begin(transformMatrix: transform);

Why this order? The camera transform represents how world coordinates map to screen coordinates. When you zoom (scale), you want to zoom around the camera's target point, not around the screen origin. By scaling first, the translation adjustment remains at world scale, so a 100-unit camera pan stays 100 units regardless of zoom level.

// Wrong: translate first, then scale
var badTransform = translation * scaling;
// Result: Translation is scaled too! A 100-unit pan becomes 200-unit pan at 2x zoom

// Correct: scale first, then translate  
var goodTransform = scaling * translation;
// Result: Translation happens at world scale, zoom is applied to final coordinates

Matrix multiplication note: In MonoGame, transformations are applied right-to-left: A * B means "apply B first, then A". So scaling * translation applies translation first to world coordinates, then scaling to screen coordinates.

Conversion Functions

Screen ↔ World

// World to Screen: apply camera transform
Vector2 WorldToScreen(Vector2 worldPosition, Camera camera)
{
    return Vector2.Transform(worldPosition, camera.Transform);
}

// Screen to World: invert camera transform
Vector2 ScreenToWorld(Vector2 screenPosition, Camera camera)
{
    Matrix inverse;
    Matrix.Invert(ref camera.Transform, out inverse);
    return Vector2.Transform(screenPosition, inverse);
}

World ↔ Grid

// World to Grid: divide by cell size and truncate
Vector2 WorldToGrid(Vector2 worldPosition, Grid grid)
{
    var localX = worldPosition.X - grid.Origin.X;
    var localY = worldPosition.Y - grid.Origin.Y;
    return new Vector2(
        (int)(localX / grid.GridCellSize),
        (int)(localY / grid.GridCellSize)
    );
}

// Grid to World: multiply by cell size and add origin
Vector2 GridToWorld(Vector2 gridPosition, Grid grid)
{
    return new Vector2(
        grid.Origin.X + gridPosition.X * grid.GridCellSize,
        grid.Origin.Y + gridPosition.Y * grid.GridCellSize
    );
}

Screen ↔ Grid (Combined)

// Screen to Grid: combine screen-to-world and world-to-grid
Vector2 ScreenToGrid(Vector2 screenPosition, Camera camera, Grid grid)
{
    var world = ScreenToWorld(screenPosition, camera);
    return WorldToGrid(world, grid);
}

// Grid to Screen: combine grid-to-world and world-to-screen
Vector2 GridToScreen(Vector2 gridPosition, Camera camera, Grid grid)
{
    var world = GridToWorld(gridPosition, grid);
    return WorldToScreen(world, camera);
}

Common Patterns

Picking / Hit Testing

  1. Read mouse position (screen coordinates)
  2. Convert to world coordinates using inverse camera transform
  3. Convert to grid coordinates for tile selection
  4. Bounds check against valid grid area
var mouseScreen = new Vector2(Mouse.GetState().X, Mouse.GetState().Y);
var world = ScreenToWorld(mouseScreen, camera);
var gridPos = WorldToGrid(world, grid);

if (gridPos.X >= 0 && gridPos.X < grid.Width && gridPos.Y >= 0 && gridPos.Y < grid.Height)
{
    // Valid tile selected
}

Render Culling

Convert visible screen area to world coordinates to determine which tiles need rendering:

// Get screen bounds in world coordinates
var screenTopLeft = ScreenToWorld(Vector2.Zero, camera);
var screenBottomRight = ScreenToWorld(new Vector2(GraphicsDevice.Viewport.Width, GraphicsDevice.Viewport.Height), camera);

// Convert to grid coordinates for culling
var gridTopLeft = WorldToGrid(screenTopLeft, grid);
var gridBottomRight = WorldToGrid(screenBottomRight, grid);

// Only render tiles within this range

Camera Follow

Keep a target entity centered on screen:

// Center camera on entity (in world space)
var targetWorld = entity.Position;
var screenCenter = new Vector2(viewportWidth / 2f, viewportHeight / 2f);

// Camera translation should move target to screen center
var cameraTranslation = screenCenter - targetWorld;

// Update camera transform
camera.Transform = Matrix.CreateTranslation(cameraTranslation.X, cameraTranslation.Y, 0);

RT4X Rules

Separate concerns
Keep your coordinate conversion logic in a dedicated utility class or methods on your Grid and Camera classes. Don't scatter conversion math throughout your codebase.
Choose a world unit
Decide what one world unit represents (1 meter? 1 foot? 1 tile width?) and be consistent. Many 2D games use tile size as the world unit, so GridToWorld becomes trivial multiplication.
Bounds checking
Always validate grid coordinates after conversion. Screen corners can map to negative or out-of-bounds grid positions. Typical validation: gridPos.X >= 0 && gridPos.X < grid.Width && gridPos.Y >= 0 && gridPos.Y < grid.Height. This prevents array index exceptions and ensures your spatial queries stay within valid game area.
Order matters
Matrix multiplication is not commutative. Scale * Translate gives different results than Translate * Scale.

Implementation Checklist

  1. Create a static CoordinateUtils or Transforms class
  2. Implement Screen↔World methods (requires Camera or transform matrix)
  3. Implement World↔Grid methods (requires Grid configuration)
  4. Implement Screen↔Grid as combinations
  5. Add unit tests for each conversion direction
  6. Integrate with existing Grid class
