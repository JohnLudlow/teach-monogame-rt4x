Terrain generation pipeline

Keep what occupies a tile separate from how to choose it and how to draw it. The present world is a 32 × 16 2D grid; later map-generation requirements add constraints, levels, and regions without turning camera pixels into world identity.

Data flow

dimensions + seed
    → generator (one local RNG, fixed cell order)
    → terrain[x, y] (one type per cell)
    → colour + GridToWorldRect(x, y)
    → SpriteBatch with camera.Transform

Generate once, then render the stored map every frame. Draw terrain before grid lines, settlements, and hover overlay. Settlements continue to use their stable cell coordinates.

Different jobs, different techniques

QuestionToolNot guaranteed by that tool
How do I reproduce a first terrain map?Seeded random choices per tileCoherent coastlines or valid neighbours
Which terrain types may touch?Simple tiled WFC with explicit adjacency rules and propagationAdministrative regions or rivers
Which larger region owns a location?Voronoi seeds and nearest-seed regionsTile adjacency rules or biome transitions
Which tile is at this location underground?A level-aware map coordinate and per-level dataAny particular generation algorithm

These stages can be combined later, but their order and interaction need deliberate design. A Voronoi region may contain many tiles; it is not automatically a biome, province, or water basin. WFC constraints do not by themselves model downhill river flow.

Small contract checklist

  • Can every in-bounds Point return one terrain type, and does an invalid Point fail explicitly?
  • Are the same dimensions and seed reproducible within the current generator and runtime?
  • Does generation run once, without depending on SpriteBatch, Camera, or mouse state?
  • Are colours assigned at rendering time using GridToWorldRect and the existing camera transform?
  • Are adjacency, z-levels, rivers, and regions still labelled as future work rather than implied by random tiles?
