Lesson 8 — An input command layer (and drag-panning)

In Lesson 7 you read the keyboard and mouse directly inside Game1.Update and mutated the camera on the spot. That works, but it hard-wires which device does what into the game loop. This lesson lifts input out of Game1 — the same move you made for coordinate math in Lesson 6 — into a small command layer: devices produce device-agnostic commands, and a CameraController applies them. Adding middle-mouse drag-panning then costs almost nothing, because a drag just emits the same Pan command a key does.

Why a command layer

Lesson 7's Update answers "what does the D key do?" with "mutate the camera, here, now". That couples three separate concerns: which device was used, what it means, and how the camera responds. Untangling them buys you:

  • Rebinding. If a key is just one way to produce a Pan command, then a mouse drag, a gamepad stick, or a remapped key can all produce the same command — without touching the camera code.
  • Testability. Command production becomes a pure function of (input state, previous state, bindings). You can feed it two MouseStates and assert the commands, with no graphics device — unlike Lesson 7's inline input, which couldn't be unit-tested at all.
  • Future reach. The same command stream can later come from AI, a replay file, or the network. The camera doesn't care what produced a Pan.

The cost is a few small types. That is a real tradeoff — for a throwaway prototype it would be over-engineering. You're doing it because you named concrete future needs (rebinding, input config) that justify the seam now.

The shape: commands, bindings, reader, controller

Four pieces, split by their ECS-style role — data versus behaviour:

InputCommand (command — Core/Commands)
A device-agnostic intent. A small record hierarchy: PanCommand(Vector2 WorldDelta) and ZoomCommand(float Factor, Vector2 FocusScreen).
InputBindings (data — Core/Components/Input)
Which device inputs mean what: pan keys, pan speed, the drag button, zoom step. The rebindable part — swap the instance, behaviour changes, no logic edits.
InputReader (behaviour — Core/Systems/Input)
Reads keyboard/mouse + previous frame + dt + bindings, and produces a list of InputCommands. Holds per-frame state (previous scroll value, drag anchor).
CameraController (behaviour — Core/Systems/Input)
Applies each command to the Camera. Keeps Camera a pure data/transform holder (good for ECS: data separate from the system that acts on it).

A note on the folders

The layout separates types by ECS-style role: Core/Entities (identities like Camera), Core/Systems (behaviour), Core/Components (data attached to entities), and Core/Commands (transient intents). InputCommand is a command, so it lives in Core/Commands, not with the components. InputBindings is config data, grouped under Components/Input as a data-shaped type until real components are formalised.

Step 1 — InputCommand + InputBindings

Create Core/Commands/InputCommand.cs. A sealed record hierarchy models the fixed set of intents, and pattern-matching in the controller stays exhaustive:

using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core.Commands;

public abstract record InputCommand;

/// A request to move the camera by a world-space delta.
public sealed record PanCommand(Vector2 WorldDelta) : InputCommand;

/// A request to multiply zoom by Factor, keeping FocusScreen fixed on screen.
public sealed record ZoomCommand(float Factor, Vector2 FocusScreen) : InputCommand;

Then Core/Components/Input/InputBindings.cs. Keep it plain data with sensible defaults; every value here is a candidate for a future config file:

using Microsoft.Xna.Framework.Input;

namespace FourxGame.MonoGame.Core.Components.Input;

public sealed class InputBindings
{
    public Keys PanUp { get; init; } = Keys.W;
    public Keys PanDown { get; init; } = Keys.S;
    public Keys PanLeft { get; init; } = Keys.A;
    public Keys PanRight { get; init; } = Keys.D;

    public float PanSpeed { get; init; } = 400f;   // world units / second
    public float ZoomStep { get; init; } = 0.1f;   // fraction per wheel notch

    // Which mouse button grabs the world to drag-pan.
    public DragButton DragPanButton { get; init; } = DragButton.Middle;
}

public enum DragButton { None, Left, Middle, Right }

Referencing the drag button through InputBindings (not a hard-coded MiddleButton) is what makes it configurable later — a data change, not a code change, exactly as you asked.

Step 2 — InputReader produces commands

Create Core/Systems/Input/InputReader.cs. It turns raw device state into commands. Keyboard panning is the frame-rate-independent logic from Lesson 7, now emitting a PanCommand instead of calling the camera. Note the reader takes the current keyboard/mouse state and dt as parameters — it does not call Keyboard.GetState() itself, so it stays testable.

using System.Collections.Generic;
using FourxGame.MonoGame.Core.Commands;
using FourxGame.MonoGame.Core.Components.Input;
using Microsoft.Xna.Framework;
using Microsoft.Xna.Framework.Input;

namespace FourxGame.MonoGame.Core.Systems.Input;

public sealed class InputReader(InputBindings bindings)
{
    private int _previousScroll;
    private Point? _dragAnchor;   // screen position where the current drag began

    public IReadOnlyList<InputCommand> Produce(
        KeyboardState keyboard, MouseState mouse, float zoom, float dt)
    {
        var commands = new List<InputCommand>();

        // --- keyboard pan (world units/second, normalised so diagonals aren't faster) ---
        var pan = Vector2.Zero;
        if (keyboard.IsKeyDown(bindings.PanLeft))  pan.X += 1;
        if (keyboard.IsKeyDown(bindings.PanRight)) pan.X -= 1;
        if (keyboard.IsKeyDown(bindings.PanUp))    pan.Y += 1;
        if (keyboard.IsKeyDown(bindings.PanDown))  pan.Y -= 1;
        if (pan != Vector2.Zero)
        {
            pan.Normalize();
            commands.Add(new PanCommand(pan * bindings.PanSpeed * dt));
        }

        // --- wheel zoom (ScrollWheelValue is cumulative; take the delta) ---
        var scrollDelta = mouse.ScrollWheelValue - _previousScroll;
        _previousScroll = mouse.ScrollWheelValue;
        if (scrollDelta != 0)
        {
            var factor = 1f + (scrollDelta / 120f) * bindings.ZoomStep;
            commands.Add(new ZoomCommand(factor, new Vector2(mouse.X, mouse.Y)));
        }

        // --- Step 3 adds drag-panning here ---

        return commands;
    }
}

Passing zoom in looks unused so far — Step 3 needs it for the drag math. Leave the parameter in now so the signature is stable.

Step 3 — Add middle-mouse drag-panning

Drag-panning: while the bound button is held, moving the mouse grabs the world and slides it. The subtlety — the same "keep the point under the pointer" idea as zoom-to-cursor — is that a screen drag of N pixels must move the world by N / zoom world units, or the grabbed tile slides out from under the cursor when zoomed.

Add this where the comment sits in Produce, plus a small helper to read the bound button:

// --- drag pan ---
var dragDown = IsDragButtonDown(mouse, bindings.DragPanButton);
var mousePoint = new Point(mouse.X, mouse.Y);

if (dragDown && _dragAnchor is Point anchor)
{
    var screenDelta = mousePoint - anchor;                 // pixels moved this frame
    if (screenDelta != Point.Zero)
    {
        // divide by zoom so the grabbed world point stays under the cursor
        var worldDelta = new Vector2(screenDelta.X, screenDelta.Y) / zoom;
        commands.Add(new PanCommand(worldDelta));
    }
    _dragAnchor = mousePoint;                               // re-anchor for next frame
}
_dragAnchor = dragDown ? mousePoint : null;                // start / clear the drag
private static bool IsDragButtonDown(MouseState mouse, DragButton button) => button switch
{
    DragButton.Left   => mouse.LeftButton   == ButtonState.Pressed,
    DragButton.Middle => mouse.MiddleButton == ButtonState.Pressed,
    DragButton.Right  => mouse.RightButton  == ButtonState.Pressed,
    _ => false,
};

Because drag emits a PanCommand — the very same type the keyboard emits — the camera side needs no new code to support it. That is the whole point of the command layer.

Sign check

Dragging the mouse right should pull the world right (grab-and-drag feel), so a positive screen delta becomes a positive world delta here — the opposite intent from the keyboard "look right" convention in Lesson 7. Both are valid; they're just different gestures. Decide each deliberately and note it in your bindings.

Step 4 — CameraController applies commands

Create Core/Systems/Input/CameraController.cs. It executes commands against the camera. The ZoomCommand carries the zoom-toward-point logic from Lesson 7 — using Transforms.ScreenToWorld and Camera.Pan, no new math:

using System.Collections.Generic;
using FourxGame.MonoGame.Core.Commands;
using FourxGame.MonoGame.Core.Entities;
using FourxGame.MonoGame.Core.Utilities;
using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core.Systems.Input;

public sealed class CameraController(Camera camera)
{
    public void Apply(IReadOnlyList<InputCommand> commands)
    {
        foreach (var command in commands)
        {
            switch (command)
            {
                case PanCommand pan:
                    camera.Pan(pan.WorldDelta);
                    break;

                case ZoomCommand zoom:
                    var before = Transforms.ScreenToWorld(zoom.FocusScreen, camera.Transform);
                    camera.Zoom *= zoom.Factor;    // Camera clamps [0.1, 5]
                    var after = Transforms.ScreenToWorld(zoom.FocusScreen, camera.Transform);
                    camera.Pan(after - before);    // keep the focus point fixed on screen
                    break;
            }
        }
    }
}

The switch on the sealed record hierarchy makes the intent explicit and easy to extend: a future SelectCellCommand adds one case, and nothing else changes.

Step 5 — Rewire Game1

Now Game1 owns the reader, controller, and bindings, and its Update shrinks to "read devices → produce commands → apply them". All the input logic has left Game1:

// fields
private InputReader _input = null!;
private CameraController _cameraController = null!;

// in Initialize(), after _camera is created:
_input = new InputReader(new InputBindings());
_cameraController = new CameraController(_camera);

// Update()
var dt = (float)gameTime.ElapsedGameTime.TotalSeconds;
var commands = _input.Produce(Keyboard.GetState(), Mouse.GetState(), _camera.Zoom, dt);
_cameraController.Apply(commands);

// picking is unchanged — still one line, still the shared transform:
_hoveredCell = _grid.ScreenToGrid(new Vector2(Mouse.GetState().X, Mouse.GetState().Y), _camera.Transform);

Reading Mouse.GetState() twice per frame is harmless but slightly wasteful — consider capturing it once into a local and passing it to both. A small tidy, your call.

Testing the seam

This is the reward for the abstraction: InputReader is now unit-testable without a window. You can construct KeyboardState and MouseState directly (their constructors accept the raw values) and assert the commands produced. Aim for:

  • Holding a pan key emits one PanCommand with the expected world delta for a given dt.
  • No input emits no commands.
  • A wheel-value change emits a ZoomCommand with the focus at the mouse position; equal values emit none.
  • With the drag button held and the mouse moved, the emitted PanCommand.WorldDelta equals screenDelta / zoom (test at zoom 1 and zoom 2 to prove the division).

Ask me for help if constructing the input states is fiddly — the MouseState constructor takes position, scroll, and button states in a specific order.

Retrieval check

Answer all three before opening the answers:

  1. Why can middle-mouse drag reuse the camera code unchanged, when the keyboard already pans?
  2. When drag-panning while zoomed to 2×, why divide the screen delta by the zoom?
  3. What makes InputReader unit-testable now, when Lesson 7's inline input was not?
Show answers
  1. Both produce the same PanCommand; the CameraController applies commands regardless of which device produced them.
  2. At 2× zoom, one world unit covers two screen pixels, so a screen drag of N pixels is only N/2 world units — dividing keeps the grabbed point under the cursor.
  3. It takes device state and dt as parameters and returns commands as data, with no graphics device or static input calls — a pure function you can feed constructed states.
