Lesson 9 — Place a settlement on a tile

Your grid is no longer just something to point at: it becomes a world where an action has a durable result. In this lesson, a left click places one gold settlement marker on the pointed tile. The marker stays attached while the camera pans and zooms, and clicking its tile again does not create a duplicate. This is the smallest useful vertical slice of the RT4X mission: player intent → world rule → rendered state.

World interaction (9 of the course so far). Lesson 8 made devices produce commands. Here a placement controller resolves a screen-space click through the existing camera and grid, then a world system applies the game rule. Keep the tile-placement pipeline reference nearby.

The one behaviour and its boundary

The rule is deliberately small: a settlement can occupy an in-bounds, unoccupied grid cell. A settlement stores its Point Cell, not its screen pixels or a Rectangle. Screen coordinates are only how the player points; grid coordinates are the durable world identity.

left-click at screen (x, y)
       │
       ▼
PlaceSettlementAtScreenCommand(screen position)  ← input intent
       │
       ▼
SettlementPlacementController                   ← Screen → Grid boundary
       │
       ▼
SettlementPlacementSystem.TryPlace(cell)        ← validates + changes state
       │
       ▼
DrawSettlements: cell → world rectangle → marker

This preserves the lessons already learned. The input reader still has no Grid or Camera dependency. The world system never sees screen coordinates. Only the controller, where UI intent crosses into the world, needs both.

Step 1 — Specify occupancy with tests

Start with the pure rule, before drawing. Create FourxGame.MonoGame.UnitTests/Systems/World/SettlementPlacementSystemTests.cs. These tests protect the two behaviours that later city and building placement will need: a valid empty cell succeeds; a second placement on the same cell changes nothing.

using FourxGame.MonoGame.Core.Entities;
using FourxGame.MonoGame.Core.Systems.World;
using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.UnitTests.Systems.World;

public class SettlementPlacementSystemTests
{
  private static Grid MakeGrid() => new()
  {
    GridCellSize = 48,
    GridSizeX = 32,
    GridSizeY = 16,
    Origin = Vector2.Zero
  };

  [Fact]
  public void TryPlace_EmptyInBoundsCell_AddsSettlement()
  {
    var system = new SettlementPlacementSystem(MakeGrid());
    var cell = new Point(4, 3);

    var placed = system.TryPlace(cell);

    Assert.True(placed);
    Assert.Equal(new Settlement(cell), system.Settlements[cell]);
  }

  [Fact]
  public void TryPlace_OccupiedCell_LeavesTheOriginalSettlementUntouched()
  {
    var system = new SettlementPlacementSystem(MakeGrid());
    var cell = new Point(4, 3);
    system.TryPlace(cell);

    var placedAgain = system.TryPlace(cell);

    Assert.False(placedAgain);
    Assert.Single(system.Settlements);
    Assert.Equal(new Settlement(cell), system.Settlements[cell]);
  }

  [Theory]
  [InlineData(-1, 0)]
  [InlineData(32, 0)]
  [InlineData(0, 16)]
  public void TryPlace_OffGridCell_DoesNotAddSettlement(int x, int y)
  {
    var system = new SettlementPlacementSystem(MakeGrid());

    var placed = system.TryPlace(new Point(x, y));

    Assert.False(placed);
    Assert.Empty(system.Settlements);
  }
}

Run the tests now. They should fail to compile because the types do not exist — useful red, not a problem. Notice that this is game logic with no MouseState, SpriteBatch, or window involved.

Step 2 — Store settlements by grid cell

Create the identity in Core/Entities/Settlement.cs. A record is enough for this first vertical slice: its cell is its durable identity and record equality makes the test expressive.

using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core.Entities;

public sealed record Settlement(Point Cell);

Then create Core/Systems/World/SettlementPlacementSystem.cs. A dictionary makes the occupancy rule structural: one Point key can map to at most one settlement. It also gives future code an efficient answer to “what is on this cell?”

using System.Collections.Generic;
using FourxGame.MonoGame.Core.Entities;
using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core.Systems.World;

public sealed class SettlementPlacementSystem(Grid grid)
{
  private readonly Dictionary<Point, Settlement> _settlements = [];

  public IReadOnlyDictionary<Point, Settlement> Settlements => _settlements;

  public bool TryPlace(Point cell)
  {
    if (!grid.IsValidGridPosition(cell))
    {
      return false;
    }

    return _settlements.TryAdd(cell, new Settlement(cell));
  }
}

Run the tests again. They should now pass. TryAdd is doing an important job: it returns false and preserves the original entry when the key already exists. Do not implement duplicate prevention in drawing or input; it is a world rule, so it belongs here.

Step 3 — Express a placement click

Add this record in a new Core/Commands/WorldCommands.cs file. It joins the existing InputCommand hierarchy from Lesson 8:

using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core.Commands;

/// A request to place a settlement at a pointed screen position.
public sealed record PlaceSettlementAtScreenCommand(Vector2 ScreenPosition) : InputCommand;

Why does an otherwise device-agnostic command carry a screen coordinate? It is a boundary value, not world state. The command says what the player intends, while preserving the one fact needed to resolve that intent after camera commands in the same frame. The next step converts it immediately; no settlement will store this position.

Step 4 — Emit once per click, not once per frame

Add a field and a helper to InputReader. Call the helper from Produce after the existing mouse handlers. The edge test means holding the button down across ten updates produces exactly one command, rather than ten settlements.

// field
private bool _wasPlaceButtonDown;

// near the other handler calls in Produce(...)
HandlePlaceSettlementClick(mouse, commands);
private void HandlePlaceSettlementClick(
  MouseState mouse,
  List<InputCommand> commands)
{
  var isPlaceButtonDown = mouse.LeftButton == ButtonState.Pressed;

  if (isPlaceButtonDown && !_wasPlaceButtonDown)
  {
    commands.Add(
      new PlaceSettlementAtScreenCommand(new Vector2(mouse.X, mouse.Y)));
  }

  _wasPlaceButtonDown = isPlaceButtonDown;
}

Use left click only for this prototype. Middle click is already reserved for drag-panning, so these gestures do not compete. A later lesson can make the selected build tool and its binding configurable; do not build a tool palette now.

Add this focused input test beside your existing input tests. It is required coverage for the new input behaviour: it proves the press edge rather than merely asserting that a reader can be constructed. Add using System.Linq; if your project does not already supply it through implicit usings.

[Fact]
public void Produce_HeldLeftClick_EmitsOnlyOnePlacementCommand()
{
  var reader = new InputReader(new InputBindings());
  var released = new MouseState(100, 100, 0,
    ButtonState.Released, ButtonState.Released, ButtonState.Released,
    ButtonState.Released, ButtonState.Released);
  var pressed = new MouseState(100, 100, 0,
    ButtonState.Pressed, ButtonState.Released, ButtonState.Released,
    ButtonState.Released, ButtonState.Released);

  reader.Produce(new KeyboardState(), released, 1f, 0.016f);
  var firstFrame = reader.Produce(new KeyboardState(), pressed, 1f, 0.016f);
  var heldFrame = reader.Produce(new KeyboardState(), pressed, 1f, 0.016f);

  Assert.Single(firstFrame.OfType<PlaceSettlementAtScreenCommand>());
  Assert.Empty(heldFrame.OfType<PlaceSettlementAtScreenCommand>());
}

Step 5 — Resolve screen space at the boundary

Create Core/Systems/World/SettlementPlacementController.cs. It consumes the click intent, converts it using the same Grid.ScreenToGrid path as hover picking, and invokes the domain rule only when the result is a valid cell.

using System.Collections.Generic;
using FourxGame.MonoGame.Core.Commands;
using FourxGame.MonoGame.Core.Entities;

namespace FourxGame.MonoGame.Core.Systems.World;

public sealed class SettlementPlacementController(
  Grid grid,
  Camera camera,
  SettlementPlacementSystem settlements)
{
  public void Apply(IReadOnlyList<InputCommand> commands)
  {
    foreach (var command in commands)
    {
      if (command is not PlaceSettlementAtScreenCommand place)
      {
        continue;
      }

      var cell = grid.ScreenToGrid(place.ScreenPosition, camera.Transform);
      if (cell is not null)
      {
        settlements.TryPlace(cell.Value);
      }
    }
  }
}

Now write the transform-sensitive test. It proves that a click remains correct through the camera transform — a critical regression test for a strategy game, not a test of implementation detail.

[Fact]
public void Apply_PlaceCommand_MapsScreenPositionThroughCameraToTheTargetCell()
{
  var grid = MakeGrid();
  var camera = new Camera { Zoom = 2f, Position = new Vector2(100, 40) };
  var settlements = new SettlementPlacementSystem(grid);
  var controller = new SettlementPlacementController(grid, camera, settlements);

  // At this camera transform, world (200, 150) appears at screen (500, 340).
  controller.Apply([new PlaceSettlementAtScreenCommand(new Vector2(500, 340))]);

  Assert.Contains(new Point(4, 3), settlements.Settlements.Keys);
}

Order matters: in Game1, apply CameraController first, then this controller. A wheel or pan command and a click in one update therefore resolve against the camera state that will be drawn that frame.

Step 6 — Wire and draw the marker

Add fields to Game1:

private SettlementPlacementSystem _settlements = null!;
private SettlementPlacementController _settlementPlacementController = null!;

After constructing the camera in Initialize, construct the two systems:

_settlements = new SettlementPlacementSystem(_grid);
_settlementPlacementController = new SettlementPlacementController(
  _grid, _camera, _settlements);

In Update, keep the existing command production, then route the same command list to the camera and placement controllers in this order:

_cameraController.Apply(commands);
_settlementPlacementController.Apply(commands);

_hoveredCell = _grid.ScreenToGrid(
  new Vector2(mouseState.X, mouseState.Y),
  _camera.Transform);

Finally, call DrawSettlements inside the existing world-space SpriteBatch.Begin(transformMatrix: _camera.Transform) block, after the grid and before the hovered-cell overlay:

DrawGrid(_spriteBatch, _grid);
DrawSettlements(_spriteBatch, _grid);
DrawHoveredCell(_spriteBatch, _grid);

Use the existing 1×1 _pixel; do not add art or content-pipeline work for a proof marker:

private void DrawSettlements(SpriteBatch spriteBatch, Grid grid)
{
  foreach (var settlement in _settlements.Settlements.Values)
  {
    var tile = grid.GridToWorldRect(settlement.Cell);
    const int markerSize = 20;
    var marker = new Rectangle(
      tile.Center.X - markerSize / 2,
      tile.Center.Y - markerSize / 2,
      markerSize,
      markerSize);

    spriteBatch.Draw(_pixel, marker, Color.Gold);
  }
}

The marker is drawn in world coordinates and goes through the same camera transform as the grid. It will therefore pan and zoom with its tile without any special camera code. The hovered red cell is intentionally drawn last so it remains a clear interaction cue.

Fast feedback

  1. Run dotnet test FourxGame.MonoGame.UnitTests/FourxGame.MonoGame.UnitTests.csproj. All placement tests should pass.
  2. Run dotnet build monogame-rt4x.slnx.
  3. Run dotnet run --project FourxGame.MonoGame/FourxGame.MonoGame.csproj.

Success looks like: left-clicking an in-grid tile creates one gold square centred on it; holding the button does not create repeated state; clicking outside the grid changes nothing; clicking an occupied tile leaves one marker; pan, zoom, and drag leave every marker glued to its tile.

If something looks wrong

Marker offset from its tile? Use GridToWorldRect and its Center, not raw pixel math. Marker drifts while panning? Verify the settlement draw remains inside the SpriteBatch block with _camera.Transform. Dozens of markers from one hold? Check that _wasPlaceButtonDown is updated after the edge test. Wrong tile after zoom? Confirm the placement controller uses grid.ScreenToGrid(..., camera.Transform), never direct division of screen pixels.

Retrieval check

Answer before opening the feedback. Retrieval is what turns today’s implementation into a reusable design instinct.

  1. Which coordinate system should a stored settlement use: screen, world, or grid?
  2. What precise condition turns a held left mouse button into one placement command?
  3. Why does the placement controller, rather than InputReader, own the Screen → Grid conversion?
Show answers
  1. Grid. The cell is the stable map identity and stays meaningful as the camera changes. Rendering can derive a world rectangle from it.
  2. The button is pressed this update and was not pressed in the preceding update: isDown && !_wasPlaceButtonDown.
  3. InputReader translates devices into intent and has no world dependencies. The controller is the boundary that knows the intent, grid, and camera transform needed to resolve it.

What you have now

You have the first persistent world object in your fantasy RT4X: a click becomes an intent, valid world state is stored by cell, and that state is rendered through the camera. Do not add city menus, production, or art yet. The next good increment is to select an existing settlement versus placing one, or to give the settlement a simple terrain rule.
