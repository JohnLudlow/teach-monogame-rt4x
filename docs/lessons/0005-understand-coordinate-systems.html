The coordinate spaces you have

A 2D strategy game juggles several coordinate spaces at once. Each answers a different question, and confusion between them is the source of most "why is my click in the wrong place" bugs.

Screen / input space — pixels, origin at the window's top-left
Where the mouse is. Mouse.GetState() reports here. Your grid in Lessons 3–4 was drawn directly in this space, which is why the math was so short.
World space — game units, an arbitrary fixed origin
Where things are in the game, independent of the camera. A unit standing at world (2000, 1500) stays there whether the camera looks at it or not.
Grid space — whole cells, origin at cell (0, 0)
Which tile. Pathfinding, tile selection, and spatial queries all work here. Grid space is world space divided by the cell size, offset by the grid's origin.
Local / entity space — relative to a parent
Used later for sprite anchors and child objects. You don't need it yet, but the reference lists it so the picture is complete.

The key mental shift: screen space and world space are only the same while the camera is the identity transform. Right now they are. As soon as you can pan or zoom, they diverge, and you must convert deliberately.

How a transform moves between them

A transform matrix encodes a translation (pan) and a scale (zoom) in one object. MonoGame's SpriteBatch.Begin(transformMatrix: …) applies it to everything drawn in that batch, which is how a camera "moves the world" without touching any entity's stored position.

  • World → Screen: multiply a world position by the camera transform. This is what the GPU effectively does to every sprite when you pass the matrix to Begin.
  • Screen → World: multiply a screen position by the inverse of the camera transform. Use Matrix.Invert — not Matrix.Transpose, which only inverts pure rotations, not scale or translation.

Order matters. Matrix multiplication is not commutative. For a camera you build the transform as scale first, then translate:

// Camera transform: zoom, then position the world under the view
var transform = Matrix.CreateScale(Zoom)
              * Matrix.CreateTranslation(Position.X, Position.Y, 0);

Swap the two factors and the zoom would pivot around the wrong point. The reference's Combining Transforms section explains why.

The conversion chain

Every conversion you will ever need is a walk along this chain. You never jump spaces directly; you compose one step at a time:

Screen  ⇄  World  ⇄  Grid
   (camera)   (grid origin + cell size)
  • World → Grid: subtract the grid origin, divide by cell size, then floor to a whole cell.
  • Grid → World: multiply the cell by cell size, add the grid origin (and half a cell if you want the centre).
  • Screen → Grid: there is no shortcut — go Screen → World → Grid.
  • Grid → Screen: likewise Grid → World → Screen.

This is why Lesson 4's inline math only worked in screen space: with no camera, the Screen ⇄ World step was invisible, so "screen" and "world" were the same numbers. Lesson 6 makes that step real.

Traps worth knowing before you code

Rounding toward zero breaks negatives
C#'s (int) cast truncates toward zero, so a world position just left of the origin (say -1) casts to cell 0 instead of -1. Two different world positions collapse onto the same cell across the origin line. Use Math.Floor, which always rounds down, so the mapping stays consistent for negative coordinates. Lesson 6 uses Math.Floor for exactly this reason.
Invert, don't transpose
To go Screen → World you need the true inverse of the camera transform. Matrix.Transpose is a cheaper shortcut that is only correct for rotation-only matrices. Your camera has scale and translation, so use Matrix.Invert.
Always bounds-check after converting
Screen corners can map to negative or out-of-range grid cells. Validate against [0, GridSizeX) and [0, GridSizeY) before using a cell as an array index.
Float for world, int for grid
World positions are Vector2 (sub-pixel precision matters for smooth movement). Grid coordinates are whole cells — a Point — once you have floored them.

Retrieval check

Answer all three before opening the answers. Say them aloud or write them down — effortful recall is what makes this stick.

  1. To convert a mouse position to a tile, which two spaces do you pass through, in order?
  2. Which method inverts a camera transform that has scale and translation?
  3. Why use Math.Floor rather than an (int) cast when computing a grid cell?
Show answers
  1. Screen → World → Grid. There is no direct screen-to-grid step; you compose the two conversions.
  2. Matrix.Invert. Matrix.Transpose only inverts rotation-only matrices, not scale or translation.
  3. Math.Floor always rounds down, so negative world coordinates map to the correct cell; an (int) cast truncates toward zero and collapses cells across the origin.
