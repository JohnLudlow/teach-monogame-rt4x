Lesson 6 — Build coordinate utilities and camera

In Lesson 4 you converted a mouse position to a grid cell with a few lines of inline math inside Game1. In Lesson 5 you learned the coordinate spaces and the traps. Now you'll lift that math out of Game1 into a small, testable set of classes — a static Transforms utility, a Camera that owns the view matrix, and convenience methods on your existing Grid — so that pointing keeps working even once the camera can pan and zoom.

Why refactor now

Your Lesson 4 Update holds the conversion inline:

var localX = mouse.X - gridOriginX;
var localY = mouse.Y - gridOriginY;
var column = localX / CellSize;
var row    = localY / CellSize;

It works, but it has three problems that will bite as the game grows:

  • It will be duplicated. The next feature that needs a cell from a mouse position copies these lines, and now two places must stay in sync.
  • It has no camera. The math assumes screen space equals world space. That assumption breaks the instant you pan or zoom.
  • It can't be unit-tested. The logic is trapped inside Game1, which needs a running graphics device.

You'll fix all three by moving the math into classes that don't depend on Game1, matching the "separate concerns" rule from the reference.

The three classes

Transforms — static utility
Pure conversion functions. No state, no dependency on a specific grid or camera instance. Easy to unit-test.
Camera — instance class
Owns Position, Zoom, and the view Transform matrix. Everything Screen ⇄ World goes through it.
Grid — your existing class, extended
Gains convenience methods that wrap Transforms using its own Origin and GridCellSize, plus bounds checking.

Step 1 — Create the Transforms utility

Create FourxGame.MonoGame.Core/Transforms.cs. These are the conversion-chain steps from Lesson 5, written once:

using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core;

public static class Transforms
{
    // Screen -> World: invert the camera transform
    public static Vector2 ScreenToWorld(Vector2 screenPos, Matrix cameraTransform)
    {
        Matrix.Invert(ref cameraTransform, out var inverse);
        return Vector2.Transform(screenPos, inverse);
    }

    // World -> Screen: apply the camera transform
    public static Vector2 WorldToScreen(Vector2 worldPos, Matrix cameraTransform)
        => Vector2.Transform(worldPos, cameraTransform);

    // World -> Grid: subtract origin, divide by cell size, floor to a whole cell
    public static Point WorldToGrid(Vector2 worldPos, Vector2 origin, int gridCellSize)
    {
        var localX = worldPos.X - origin.X;
        var localY = worldPos.Y - origin.Y;
        return new Point(
            (int)Math.Floor(localX / gridCellSize),
            (int)Math.Floor(localY / gridCellSize)
        );
    }

    // Grid -> World: multiply by cell size, add origin (returns the cell centre)
    public static Vector2 GridToWorld(Point gridPos, Vector2 origin, int gridCellSize)
        => new(
            origin.X + gridPos.X * gridCellSize + gridCellSize / 2f,
            origin.Y + gridPos.Y * gridCellSize + gridCellSize / 2f
        );
}

Why Math.Floor: as Lesson 5 warned, an (int) cast truncates toward zero, so a world position at -1 would land in cell 0 instead of -1. Math.Floor keeps negative coordinates mapping to the correct cell.

Step 2 — Create the Camera

Create FourxGame.MonoGame.Core/Camera.cs. The Transform is computed lazily, so it is rebuilt only when Position or Zoom actually changes:

using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core;

public class Camera
{
    private Vector2 _position = Vector2.Zero;
    private float _zoom = 1.0f;
    private Matrix _transform;
    private bool _dirty = true;

    public Vector2 Position
    {
        get => _position;
        set { _position = value; _dirty = true; }
    }

    public float Zoom
    {
        get => _zoom;
        // clamp so the view can't invert or zoom to nothing
        set { _zoom = Math.Clamp(value, 0.1f, 5.0f); _dirty = true; }
    }

    public Matrix Transform
    {
        get
        {
            if (_dirty)
            {
                // scale first (zoom), then translate (pan) — order matters
                _transform = Matrix.CreateScale(_zoom)
                           * Matrix.CreateTranslation(_position.X, _position.Y, 0);
                _dirty = false;
            }
            return _transform;
        }
    }

    public void Pan(Vector2 delta) => Position += delta;
}

Design note: because Transform is a lazy getter, callers never have to remember to "rebuild" the matrix after moving the camera — the setters mark it dirty and the getter recomputes on demand. Note the matrix order matches Lesson 5: CreateScale then CreateTranslation.

Step 3 — Add Grid convenience methods

Your existing Grid already has Origin, GridCellSize, GridSizeX, and GridSizeY. Add methods that wrap Transforms and add bounds checking. Update FourxGame.MonoGame.Core/Entities/Grid.cs:

using Microsoft.Xna.Framework;

namespace FourxGame.MonoGame.Core.Entities;

public class Grid
{
    public Vector2 Origin { get; set; } = Vector2.Zero;
    public required int GridCellSize { get; set; }
    public required int GridSizeX { get; set; }
    public required int GridSizeY { get; set; }

    public Point WorldToGrid(Vector2 worldPos)
        => Transforms.WorldToGrid(worldPos, Origin, GridCellSize);

    public Vector2 GridToWorld(Point gridPos)
        => Transforms.GridToWorld(gridPos, Origin, GridCellSize);

    public bool IsValidGridPosition(Point gridPos)
        => gridPos.X >= 0 && gridPos.X < GridSizeX
        && gridPos.Y >= 0 && gridPos.Y < GridSizeY;

    // Screen -> World -> Grid, returning null when the click is off the grid
    public Point? ScreenToGrid(Vector2 screenPos, Matrix cameraTransform)
    {
        var world = Transforms.ScreenToWorld(screenPos, cameraTransform);
        var gridPos = WorldToGrid(world);
        return IsValidGridPosition(gridPos) ? gridPos : null;
    }
}

Design note: ScreenToGrid returns Point? — null means "off the grid". That folds the bounds check from Lesson 5 into the conversion, so callers can't forget it.

Step 4 — Rewire Game1

Now delete the inline math from Lesson 4 and route the hovered cell through the new classes. The whole conversion becomes a single call:

using FourxGame.MonoGame.Core;
using FourxGame.MonoGame.Core.Entities;

private Grid _grid = null!;
private Camera _camera = null!;
private Point? _hoveredCell;

protected override void Initialize()
{
    _grid = new Grid
    {
        GridCellSize = 48,
        GridSizeX = 12,
        GridSizeY = 8,
        Origin = Vector2.Zero
    };
    _camera = new Camera();
    base.Initialize();
}

protected override void Update(GameTime gameTime)
{
    var mouse = Mouse.GetState();
    var mousePos = new Vector2(mouse.X, mouse.Y);

    // replaces the inline localX/localY math from Lesson 4
    _hoveredCell = _grid.ScreenToGrid(mousePos, _camera.Transform);

    base.Update(gameTime);
}

protected override void Draw(GameTime gameTime)
{
    GraphicsDevice.Clear(Color.CornflowerBlue);

    // pass the camera transform so the world is drawn through the view
    _spriteBatch.Begin(transformMatrix: _camera.Transform);
    DrawGrid();
    DrawHoveredCellHighlight();   // uses _hoveredCell as before
    _spriteBatch.End();

    base.Draw(gameTime);
}

Keep the same grid dimensions you chose in Lessons 3–4 so the view doesn't jump. The behaviour should be identical — but the conversion now lives in one testable place, and it already understands the camera.

Fast feedback

dotnet build monogame-rt4x.slnx
dotnet run --project FourxGame.MonoGame/FourxGame.MonoGame.csproj

Success looks like:

  • The grid renders exactly where it did in Lesson 4.
  • The hovered-cell highlight still tracks the mouse cell-by-cell.
  • Moving the cursor off the grid clears the highlight (thanks to the Point? return).
  • No inline coordinate math remains in Game1.

Because Transforms and Grid no longer depend on Game1, you can now unit-test them in FourxGame.MonoGame.UnitTests: assert that WorldToGrid(GridToWorld(cell)) round-trips back to the same cell.

Retrieval check

Answer all three before opening the answers:

  1. Which class owns the view matrix, and which class turns a world position into a cell?
  2. Why does Camera.Transform use a dirty flag instead of rebuilding every frame?
  3. What does Grid.ScreenToGrid return when the mouse is outside the grid, and why is that useful?
Show answers
  1. Camera owns the view matrix; Grid (via Transforms.WorldToGrid) turns a world position into a cell.
  2. The matrix only changes when Position or Zoom changes; the dirty flag avoids recomputing it on frames where nothing moved.
  3. It returns null, which forces callers to handle "off the grid" and prevents out-of-bounds array access.

Where this goes next

You now have a camera and a clean conversion layer. The obvious next win is camera controls: map WASD or arrow keys to Camera.Pan and the mouse wheel to Camera.Zoom, then confirm the hovered-cell highlight still lands on the right tile while the view moves. That is the real payoff of doing the refactor — pointing keeps working through pan and zoom for free.
