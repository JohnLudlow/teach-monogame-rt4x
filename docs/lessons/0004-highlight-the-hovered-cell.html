Lesson 4 — Highlight the hovered cell

An RT4X map only becomes useful when the player can point at tiles intentionally. Your grid now renders; next, make the game detect which cell the mouse is over and draw a visible highlight on that one cell.

What you need to know

Because your grid is still in screen space, mouse-to-cell mapping is simple: subtract the grid origin, divide by the cell size, and reject anything outside the configured row and column bounds. Read the mouse-to-grid-cell reference first, then keep the frame-loop reference in mind: input sampling and hovered-cell state belong in Update, while the visual highlight belongs in Draw.

You will write this conversion inline in Game1 for now. That is intentional. Doing it by hand once makes the abstraction in Lesson 6 feel earned rather than arbitrary.

Your exercise

  1. In monogame-rt4x/FourxGame.MonoGame/Game1.cs, add state for the currently hovered cell. Keep it simple: either a nullable pair of grid coordinates, or a boolean plus row and column fields.
  2. In Update, call Mouse.GetState(). Convert the mouse position into grid-local coordinates by subtracting the same origin you used to place the grid.
  3. If the mouse lands inside the grid bounds, store the hovered cell. If it lands outside, clear the hovered-cell state.
  4. In Draw, after drawing the grid, draw one translucent filled rectangle over the hovered cell. Then optionally redraw that cell's border in a stronger color so the highlight reads clearly.
  5. Move the mouse around the window. You win when exactly one cell highlights under the cursor, and no cell stays highlighted when the cursor leaves the grid.

Implementation shape

protected override void Update(GameTime gameTime)
{
    var mouse = Mouse.GetState();
    var localX = mouse.X - gridOriginX;
    var localY = mouse.Y - gridOriginY;

    // bounds check, then compute:
    // column = localX / CellSize
    // row = localY / CellSize

    base.Update(gameTime);
}

protected override void Draw(GameTime gameTime)
{
    GraphicsDevice.Clear(Color.CornflowerBlue);

    _spriteBatch.Begin();
    DrawGrid();
    DrawHoveredCellHighlight();
    _spriteBatch.End();

    base.Draw(gameTime);
}

The key design choice is that the same grid origin and cell size drive both the grid drawing and the mouse mapping. If those values diverge, input will feel haunted. (This duplication is exactly the smell Lesson 6 removes.)

Fast feedback

dotnet build monogame-rt4x.slnx
dotnet run --project FourxGame.MonoGame/FourxGame.MonoGame.csproj

Success looks like one highlight tracking the mouse cell-by-cell. If the highlight is offset, debug in this order: wrong grid origin, wrong cell size, forgotten bounds check, then row/column mixed up.

Retrieval check

Answer both prompts before opening the answer:

  1. What two numbers must be subtracted from the mouse position before dividing by CellSize?
  2. Should hovered-cell state be updated in Update or Draw?
Show answers

You subtract the grid origin: the grid's top-left x and y screen coordinates. Hovered-cell state should be updated in Update; Draw should only render the current highlight.

Where this goes next

You now have inline conversion math living in Game1. It works, but it will be copied the moment a second feature needs a cell from a mouse position. Before that happens, Lesson 5 gives you the vocabulary of coordinate systems, and Lesson 6 lifts this math out of Game1 into a reusable Transforms utility and a Camera.
