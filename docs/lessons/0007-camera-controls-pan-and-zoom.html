Lesson 7 — Camera controls: pan and zoom

You built a Camera in Lesson 6 but never moved it. This lesson wires keyboard panning and mouse-wheel zoom into Update, draws the world through the camera, and confirms the hovered-cell highlight still lands on the right tile as the view moves. That last part is the whole payoff of the refactor: because picking and drawing share one transform, pointing keeps working through pan and zoom for free.

Step 0 — Draw through the camera

Right now your Draw calls _spriteBatch.Begin() with no transform, so the world is drawn in raw screen space — the camera affects picking but not rendering. Fix that first, before adding any controls:

_spriteBatch.Begin(transformMatrix: _camera.Transform);

With an identity camera (zoom 1, position 0) this changes nothing visually — the grid renders exactly where it did. But now the camera's transform drives both drawing and picking. That shared transform is what keeps the highlight correct once the camera moves. Build and run to confirm the grid looks unchanged.

Why this must come first

If you added panning before this line, the world would sit still while your hovered cell drifted — picking would move but rendering wouldn't. Wiring the transform into Begin first means every later step moves both together.

Step 1 — Pan with the keyboard

In Update, read the keyboard and call _camera.Pan. Your Camera.Transform is CreateScale(Zoom) * CreateTranslation(Position…), so increasing Position.X shifts the drawn world to the right.

Decide the sign deliberately. Think about what the key should mean. If pressing D means "look further right" (like a strategy game scrolling the map right), the world content must move left under the viewport — so Position.X should decrease. If instead you think of the keys as "drag the world", the sign flips. There is no universally correct choice; pick one, write it down, and stay consistent. This lesson assumes camera-style ("look toward"):

var keyboard = Keyboard.GetState();
var pan = Vector2.Zero;
if (keyboard.IsKeyDown(Keys.A) || keyboard.IsKeyDown(Keys.Left))  pan.X += 1; // world moves right => look left
if (keyboard.IsKeyDown(Keys.D) || keyboard.IsKeyDown(Keys.Right)) pan.X -= 1;
if (keyboard.IsKeyDown(Keys.W) || keyboard.IsKeyDown(Keys.Up))    pan.Y += 1;
if (keyboard.IsKeyDown(Keys.S) || keyboard.IsKeyDown(Keys.Down))  pan.Y -= 1;

if (pan != Vector2.Zero)
    _camera.Pan(pan);   // temporary: fixed step, we fix the speed next

Run it. Holding a key should scroll the map. It will feel either too fast or tied to your frame rate — that's Step 2.

Step 2 — Make panning frame-rate independent

A fixed pan per frame means the camera moves faster on a 240 Hz monitor than a 60 Hz one — the game literally plays differently on different hardware. The fix is the same principle as the frame loop: scale movement by elapsed time, so speed is measured in world units per second, not per frame.

const float panSpeed = 400f; // world units per second
var dt = (float)gameTime.ElapsedGameTime.TotalSeconds;

if (pan != Vector2.Zero)
{
    pan.Normalize();               // so diagonal isn't faster than straight
    _camera.Pan(pan * panSpeed * dt);
}

Two things worth noticing: Normalize stops diagonal panning being ~1.4× faster (the length of a (1,1) vector), and multiplying by dt makes 400 units/second mean the same thing regardless of frame rate.

Step 3 — Zoom with the mouse wheel

The mouse wheel is not a per-frame delta. MouseState.ScrollWheelValue is a cumulative total since the game started (docs). To get "how much did the wheel move this frame", you must remember last frame's value and subtract:

// field on Game1:
private int _previousScroll;

// in Update, after Mouse.GetState():
var scrollDelta = mouse.ScrollWheelValue - _previousScroll;
_previousScroll = mouse.ScrollWheelValue;

if (scrollDelta != 0)
{
    // each wheel notch is ~120 units; turn it into a small multiplicative step
    var factor = 1f + (scrollDelta / 120f) * 0.1f;
    _camera.Zoom *= factor;   // Camera clamps to [0.1, 5]
}

Why multiply, not add? Zoom feels natural when each notch changes the view by a percentage, not a fixed amount — going 1×→2× should feel like 2×→4×. Multiplying by a factor gives that; adding a constant would make zooming feel sluggish when zoomed out and jumpy when zoomed in. Your Camera.Zoom setter already clamps the result, so you can't invert or collapse the view.

Step 4 — Zoom toward a point (the tricky bit)

Run Step 3 and you'll see the problem: the view zooms toward the world origin (top-left of the grid), not toward the cursor or the screen centre. That's because CreateScale scales distance from (0,0), and your camera's translation doesn't compensate.

The fix is a classic: to zoom toward a screen point p, find the world position under p before the zoom, apply the zoom, then move the camera so that same world position is under p again. Using the utilities you already have:

// zoom toward the mouse cursor
var worldBefore = Transforms.ScreenToWorld(mousePos, _camera.Transform);
_camera.Zoom *= factor;
var worldAfter = Transforms.ScreenToWorld(mousePos, _camera.Transform);
_camera.Pan(worldAfter - worldBefore);   // nudge so the cursor stays over the same tile

This is the moment the Lesson 6 investment really pays: you fix a fiddly camera behaviour using nothing but ScreenToWorld and Pan, with no new math. Try zooming to the screen centre instead by feeding a centre point rather than mousePos — same technique.

Watch the reading order

worldBefore must be read with the old zoom and worldAfter with the new zoom — that is why _camera.Zoom *= factor; sits between them. Because Transform is a lazy getter, each ScreenToWorld call automatically uses the current camera state; you don't rebuild anything by hand.

Fast feedback

dotnet build monogame-rt4x.slnx
dotnet run --project FourxGame.MonoGame/FourxGame.MonoGame.csproj

Success looks like:

  • Holding WASD / arrows scrolls the map smoothly, at the same speed regardless of frame rate.
  • Diagonal panning is the same speed as straight panning.
  • The mouse wheel zooms in and out, stopping at the clamp limits without inverting.
  • Zoom stays centred on the cursor (Step 4), not the top-left corner.
  • The red highlight still lands on the correct cell while you pan and zoom — the real proof the shared transform works.

If the highlight drifts away from the cursor as you zoom, the usual cause is drawing with a different transform than you pick with — confirm both Begin and ScreenToGrid use _camera.Transform.

Retrieval check

Answer all three before opening the answers:

  1. Why multiply the pan vector by gameTime.ElapsedGameTime.TotalSeconds?
  2. ScrollWheelValue gives you what — a per-frame delta or a running total — and what must you do to get the delta?
  3. To keep the cursor over the same tile while zooming, what three steps do you perform, in order?
Show answers
  1. To make movement frame-rate independent: speed becomes world units per second, so the camera moves the same amount on fast and slow hardware.
  2. A cumulative running total since game start. Store last frame's value and subtract it from this frame's value to get the delta.
  3. Read the world position under the cursor with the old zoom; apply the zoom; read the world position under the cursor again and pan by the difference.
