Lesson 10 — Generate a first terrain map

Turn your empty 32 × 16 grid into a repeatable, coloured terrain map. Today the map is intentionally simple: each cell receives one of three terrain types from a seeded generator. You build it in the monogame-rt4x subject repository, not in this teaching repository. This is the first visible step toward the fantasy RT4X world in map-generation issue 8, specifically the terrain-map subissue.

From interaction to world data. Lesson 9 stored settlements by grid cell. This lesson stores terrain by the same grid cell; the camera changes only how it is drawn. Keep the terrain pipeline reference nearby.

Decide what the generator owns

A terrain type is world data, not a colour. Choose a tiny set such as Water, Plains, and Forest. For this lesson, the generator receives width, height, and a seed and returns one terrain type per cell. The renderer maps types to colours and uses GridToWorldRect(cell) inside the existing camera-transformed SpriteBatch. Neither the generator nor the stored map knows about Color, SpriteBatch, mouse pixels, or zoom.

seed + dimensions → terrain generator → terrain[x, y]
                                            │
                       cell + GridToWorldRect + colour
                                            │
                                  camera-transformed Draw

Why not start with Wave Function Collapse? The original WFC project describes a simple tiled model with explicit tile-adjacency constraints and propagation; independent random choices cannot enforce “ice never touches desert.” A Voronoi map partitions space around seed points, useful later for larger regions. Neither is required just to establish and render the per-cell terrain data they will eventually consume or produce. Nor does a 2D colour array implement underground z-levels: that is a later data-model decision, not something to simulate with screen coordinates.

Step 1 — Specify the result before drawing it

In the subject repo's FourxGame.MonoGame.Core project, sketch a TerrainType enum, a read-only-to-callers terrain map with GetTerrain(Point cell), and a generator. Pick names that fit your existing Grid conventions; keep the terrain storage separate from the grid's coordinate math. Start with a focused unit test in FourxGame.MonoGame.UnitTests:

  1. A generated 32 × 16 map has terrain for every valid cell, including (0, 0) and (31, 15); reading (32, 0) or a negative index fails explicitly rather than silently returning a default.
  2. Generating twice with the same dimensions and seed returns the same terrain type at every cell. Construct a fresh generator or fresh local RNG per generation so prior calls do not consume the next map's randomness.
  3. The output contains only the terrain types you defined. Do not assert that two different seeds must differ on a tiny map: random sequences can coincide.

These tests exercise world data without constructing a game window. The success criterion is an observable contract, not a hard-coded list of pseudo-random values. For the seed behaviour, see Microsoft's seeded Random constructor; do not assume a saved seed alone promises identical maps across changes to the generator or runtime.

Step 2 — Generate and store terrain

In the subject repo, generate terrain once during initialization, not every Update or Draw. Use a local Random(seed) and visit cells in a fixed order (for example, row by row). Let each cell draw from your three terrain types, then store that value by grid coordinate. Pass dimensions from the existing Grid so the data matches its 32 × 16 bounds. Keep the seed visible in one place so you can reproduce a map when reporting a bug.

This first generator deliberately does not promise natural coastlines, valid adjacency, rivers, biomes, administrative regions, or multiple levels. Those are separate requirements in issue 8 and its subissues. Adding adjacency rules will require checking constraints while selecting cells, not merely recolouring an invalid result. A later z-level design will need to distinguish terrain at the same (x, y) on different levels; avoid treating Point as a complete 3D location.

Step 3 — Draw the map through the camera

In the subject repo's Game1.Draw, draw each terrain cell using the existing white pixel stretched over grid.GridToWorldRect(new Point(x, y)) and tinted according to its terrain type. Draw terrain before grid lines, settlement markers, and the hovered-cell overlay inside the same SpriteBatch.Begin(transformMatrix: _camera.Transform) block. Keep type-to-colour mapping at the presentation boundary, not in terrain data. SpriteBatch's official API documents its transform matrix and tinted draw overloads.

The same tile coordinates now answer three different questions: which terrain occupies this cell, can a settlement be placed here, and where should the coloured rectangle be drawn? Only the last one needs world pixels. Do not add terrain-based settlement restrictions in this lesson; existing placement should still work.

Fast feedback

  1. Run dotnet test FourxGame.MonoGame.UnitTests/FourxGame.MonoGame.UnitTests.csproj from the subject repo. Check the actual exit status as well as the test summary; the previous lesson recorded a test-runner exit-code anomaly.
  2. Run dotnet run --project FourxGame.MonoGame/FourxGame.MonoGame.csproj. You should see differently coloured tiles under the existing grid, hover highlight, and settlement markers.
  3. Restart with the same seed: the colours should stay at the same cells. Change only the seed: inspect whether the pattern changes. Pan and zoom; terrain and markers must remain aligned.

If the map looks wrong

Flickering colours? Generate once, not during drawing. Missing last row? Loop while y < GridSizeY (and similarly for x). Coloured tiles drift from settlements? Use GridToWorldRect and the same camera transform for both. Markers disappear? Draw terrain before markers.

Retrieval check

Answer these before opening the feedback, ideally after a short break. First write down your answers, then check them.

  1. Where does terrain belong: world data or drawing state? Why?
  2. Why does seeding the random generator not enforce a rule like “ice cannot border desert”?
  3. What extra coordinate will an underground tile need to distinguish it from the surface tile at the same (x, y)?
Show answers
  1. World data. Terrain is stable across camera changes; its colour is a presentation choice.
  2. A seed makes a sequence reproducible, but each independent choice still ignores its neighbours. An adjacency-constrained generator must propagate or validate those constraints.
  3. A level (or z coordinate). (x, y) by itself cannot identify both surface and underground terrain.

When you have a coloured map and the tests pass, tell me what you built and answer the retrieval check.
