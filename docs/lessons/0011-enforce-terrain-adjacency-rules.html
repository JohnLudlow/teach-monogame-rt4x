Lesson 11 — Enforce terrain adjacency rules

Make the terrain generator obey a rule supplied from outside it: two forbidden terrain types never share an edge. Keep the rule data replaceable so later biome decisions can change without rewriting generation. You implement this in monogame-rt4x, toward the placement-rules subissue; this lesson does not yet implement full Wave Function Collapse (WFC). Keep the adjacency reference handy.

From tiles to constraints. Lesson 10 made terrain data repeatable and drawable. Now keep the same cell data and renderer, but change how each type is chosen. The learner has already identified why independent seeded choices cannot satisfy neighbour rules, and why a dead end may eventually require backtracking.

Check the first terrain slice

Your current TerrainGenerator calls Random.Next((int)TerrainType.Water, (int)TerrainType.Desert). The upper bound is exclusive, so Desert is never produced. Rather than widening the numeric range and relying on enum order, provide the generator an explicit list of eligible terrain types, omitting None. Your Random is also stored on the generator: calling GenerateTerrain() twice on that instance advances the sequence. If same generator + same seed should yield the same map on both calls, create the seeded RNG inside each generation call (and test that contract). Finally, GetTerrainForCell currently returns None outside the grid; Lesson 10 called for an explicit invalid-cell failure. Choose a throwing lookup for invalid coordinates so None cannot masquerade as valid terrain. Keep these repairs in the subject repo; do not change its code in this teaching workspace.

These observations depend on the official Random.Next API. Add a test that verifies the eligible set rather than requiring every terrain type to appear in a small random sample.

Step 1 — Represent a rule, not a magic exception

For a first example only, say Water and Desert may not touch. The issue deliberately leaves real terrain rules undecided: do not bake this pair into TerrainGenerator. Define a separate rules object that accepts a finite set of eligible types and allowed unordered pairs, and answers Allows(left, right). Make Allows(a, b) equal Allows(b, a) for this direction-independent rule. Decide explicitly whether a type may border itself, and reject or explicitly exclude unknown types instead of treating a missing entry as permission.

Pass a snapshot of these rules to generation, so changing the configuration for the next map is possible without silently altering a map already generated. Start with a tiny manually specified pair table; persistence, editing UI, and biome design are later concerns. The original WFC project's simple tiled model likewise starts with tiles and adjacency data, then propagates what those constraints permit.

Step 2 — Write the behavioural tests first

Use your existing FourxGame.MonoGame.UnitTests project. These tests make the mechanism observable without committing to final world-building rules:

  1. With a rules object forbidding Water–Desert but permitting each type to touch itself and Plains, assert Allows(Water, Desert) and its reverse are both false. Build a second rules object that permits the pair and show the answer changes without modifying generator code.
  2. Generate a map from the first rule set, then inspect every horizontal and vertical neighbouring pair. Assert each pair is allowed by the supplied rules. Testing one sample cell or just counting terrain types cannot establish this guarantee.
  3. For a 2 × 1 grid with only Water eligible but Water–Water forbidden, require a clear generation failure with the seed and blocked cell, never a partial/default-filled map presented as success. This is a deliberately impossible case.
  4. Run generation twice with the same dimensions, seed, and rule snapshot. Compare every cell; changing only the rule snapshot must not mutate an already generated map.

Start with the rule-object test: it should fail before the rules exist, then pass before you integrate generation. Your generated-map test is a stronger check than “this seed looked right on screen.”

Step 3 — Filter candidates while generating

For this first rule-driven generator, keep a fixed row-by-row order. At each cell, begin with the supplied eligible types, keep those allowed beside any already assigned neighbour to the left and above, then choose among the remaining candidates with the seeded RNG. An empty candidate set is a contradiction: report the seed and cell explicitly. Do not fill with None, silently skip the cell, or present the partial array as a completed map. The current Game1 can keep drawing completed maps in the same order as Lesson 10.

for each cell in a fixed order:
    candidates = eligible types
    remove candidates forbidden beside placed neighbours
    if candidates is empty: report contradiction (seed, cell)
    otherwise: choose one candidate using the seeded RNG
after completion: verify every cardinal neighbour pair

This greedy approach is intentionally not WFC. Even when a valid map exists, an earlier choice can leave a later cell empty. Do not silently retry forever: a finite retry budget can still fail a solvable map, and cannot make an impossible rule set succeed. WFC propagates remaining possibilities beyond already fixed neighbours; adding backtracking can revisit earlier choices when a contradiction appears. The original implementation detects contradictions and can return failure; backtracking is a separate strategy, not an automatic guarantee of WFC. Once this smaller rule contract is sound, we can design bounded recovery or propagation against a concrete failing case.

Fast feedback

  1. Run your targeted rule and generator tests in the subject repo. Check the result of each adjacency assertion, not just whether the generator returned an array.
  2. Run the game and verify the coloured map still pans and zooms under settlements and hover. Visual inspection is helpful but cannot replace the exhaustive neighbour test.
  3. Deliberately supply the impossible 2 × 1 rule set: the failure must be visible with enough detail to reproduce it. Restore the normal rules afterward.

Retrieval check

Before opening the answers, write yours down from memory.

  1. Why test both Allows(Water, Desert) and Allows(Desert, Water)?
  2. Why is “same seed” insufficient to guarantee a valid adjacency rule?
  3. If filtering leaves no candidates for a cell, what can this lesson's generator say with certainty, and what can't it conclude about the rule set?
Show answers
  1. This first rule treats an edge as undirected. Reversing the pair must give the same result; later directional rules would need an explicit direction parameter.
  2. The seed only reproduces choices; validity requires a separate rule check and candidate filtering or constraint propagation.
  3. This particular sequence of choices is contradictory and must fail explicitly. The rule set may still admit a different valid map; resolving that requires revised choices, backtracking, or a more powerful solver.

Ask me follow-up questions, or bring a failed seed and its first blocked cell: tracing that concrete case will make the next step toward propagation or backtracking much easier to reason about. Do not record this lesson as completed until the subject code and tests demonstrate the rules work.
